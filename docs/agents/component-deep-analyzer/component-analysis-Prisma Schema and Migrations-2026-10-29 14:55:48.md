# Component Deep Analysis Report: Prisma Schema and Migrations (prisma/)

Analysis date: 2026-10-29 14:55:48
Scope: `prisma/` (schema, migrations, seed) plus its consumers in `src/`, `tests/`, `package.json`, `docker-compose.yml`, `.env.example`.
Ignored folders: none.

---

## 1. Executive Summary

The `prisma/` component is the persistence contract of the Order Management System (OMS) REST API. It defines the data model for a MySQL 8 database through a Prisma 5.22.0 schema (`prisma/schema.prisma`), a single initial SQL migration (`prisma/migrations/20260519182739_init/migration.sql`), a provider lock file, and a development seed script (`prisma/seed.ts`).

Role in the system: the schema generates the `@prisma/client` package that every repository and service in `src/modules/*` consumes. It also generates the `OrderStatus` and `UserRole` enums that are re-used at runtime in business logic (`src/modules/orders/order.status.ts:1`, `src/modules/orders/order.schemas.ts:2`).

Key findings:

- Seven tables: `users`, `customers`, `products`, `orders`, `order_items`, `order_status_history`, `order_number_sequence`.
- All monetary values are stored as integer cents (`priceCents`, `subtotalCents`, `discountCents`, `totalCents`, `unitPriceCents`).
- Primary keys are UUID strings (`CHAR(36)`) generated by Prisma client side (`@default(uuid())`), not by the database.
- Referential integrity is enforced by foreign keys: `RESTRICT` for references to `customers`, `users`, `products`; `CASCADE` from `orders` to `order_items` and `order_status_history`.
- The database does not enforce CHECK constraints (no non-negative stock, no positive quantity, no status-transition rule). These domain rules live only in the application layer (`src/modules/orders/*`).
- Order numbers are produced from a single-row counter table (`order_number_sequence`), incremented via `upsert` inside the order-creation transaction.
- Only one migration exists. The schema file has some formatting drift versus Prisma's canonical formatting (column alignment in `Order`, `OrderStatusHistory`, `OrderNumberSequence`), which is cosmetic.
- No automated tests target the schema or migrations directly. Coverage is indirect, through the API integration tests (`tests/auth.test.ts`, `tests/orders.test.ts`), which run against a real MySQL database.
- The seed script contains hard-coded credentials and wipes all tables on every run.

## 2. Data Flow Analysis

### 2.1 Schema to runtime (build and migration flow)

```
1. Developer edits prisma/schema.prisma
2. `npm run db:migrate` (prisma migrate dev) diffs the schema against the shadow database (SHADOW_DATABASE_URL)
3. A SQL migration is generated under prisma/migrations/<timestamp>_<name>/migration.sql
4. Migration is applied to DATABASE_URL; the history is recorded in the _prisma_migrations table (managed by Prisma)
5. prisma/migrations/migration_lock.toml pins provider = "mysql"
6. `prisma generate` (triggered by migrate dev / @prisma/client postinstall) emits the typed client
7. src/config/database.ts instantiates PrismaClient (singleton `prisma`)
8. src/app.ts:66 and src/server.ts inject the singleton into repositories and OrderService
9. Repositories/services execute queries; Prisma translates them into SQL against MySQL
```

### 2.2 Order creation (representative runtime flow touching most of the schema)

```
1. POST order -> OrderService.create (src/modules/orders/order.service.ts:50)
2. Items aggregated by productId (order.service.ts:194)
3. prisma.$transaction opened (order.service.ts:58)
4. customers read (FK target), products read, inactive products rejected
5. Totals computed server side from products.priceCents (unit price snapshot)
6. order_number_sequence upsert (id = 1) yields the next ORD-NNNNNN number (order.service.ts:245)
7. orders row created with nested order_items and an order_status_history row (fromStatus = NULL, toStatus = PENDING)
8. Transaction commit; the order is returned with relations
```

### 2.3 Status change flow

```
1. OrderService.changeStatus opens a transaction (order.service.ts:131)
2. orders row read with items
3. Same-status and invalid transitions rejected (order.status.ts)
4. PENDING->PAID: products.stockQuantity decremented; PAID/PROCESSING->CANCELLED: incremented
5. orders.status updated
6. order_status_history row inserted
7. Order re-read with relations and returned
```

### 2.4 Seed flow

```
1. `npm run db:seed` (tsx --env-file=.env prisma/seed.ts) or prisma db seed (package.json "prisma.seed")
2. All tables cleaned in FK-safe order (seed.ts:181-187)
3. Two users created with bcrypt (cost 10) hashed passwords
4. 10 customers and 20 products created
5. 26 orders created, each with an order number from reserveOrderNumber, items, computed totals, and a synthetic status history path
```

### 2.5 Error flow from database constraints

```
Prisma PrismaClientKnownRequestError
  P2002 (unique violation)  -> HTTP 409 CONFLICT (src/middlewares/error.middleware.ts:38)
  P2025 (record not found)  -> HTTP 404 NOT_FOUND (error.middleware.ts:48)
```

### Business Rule: Unique Identity Keys (email, SKU, order number)

**Overview**:
Four columns carry unique indexes: `users.email`, `customers.email`, `products.sku`, `orders.orderNumber`. They guarantee that these business identifiers cannot be duplicated.

**Detailed description**:
The schema declares `@unique` on `User.email` (prisma/schema.prisma:27), `Customer.email` (:43), `Product.sku` (:58) and `Order.orderNumber` (:76). The migration materializes them as `UNIQUE INDEX users_email_key`, `customers_email_key`, `products_sku_key`, `orders_orderNumber_key` (migration.sql:11, 26, 43, 63). Because the uniqueness is enforced by the database, it holds even under concurrent requests, which an application-level pre-check alone could not guarantee.

The application adds pre-checks for friendlier errors: for example `ProductService.create` and `update` look up the SKU first and raise `ConflictError('SKU already in use', 'SKU_ALREADY_USED')` (src/modules/products/product.service.ts:31-34, 47-52). When a race bypasses the pre-check, the unique index fires a Prisma `P2002` error, which `src/middlewares/error.middleware.ts:38-46` converts into HTTP 409 with the violated target columns in the message. Auth tests verify the duplicate email path (tests/auth.test.ts:19).

Note that `customers.document` (CPF/CNPJ) is deliberately not unique; it only has a non-unique index (schema.prisma:52). Two customers can therefore share a document. Whether that is intentional is not documented (ambiguity; confidence: medium that it is deliberate, since the index is explicit).

**Rule workflow**:
```
Insert/Update row -> MySQL unique index check
  -> unique: row persisted
  -> duplicate: error 1062 -> Prisma P2002 -> error middleware -> HTTP 409 CONFLICT
```

### Business Rule: User Roles

**Overview**:
Users have exactly one role, `ADMIN` or `OPERATOR`, stored as a MySQL ENUM, defaulting to `OPERATOR`.

**Detailed description**:
`enum UserRole { ADMIN, OPERATOR }` (schema.prisma:11-14) is mapped to `ENUM('ADMIN','OPERATOR') NOT NULL DEFAULT 'OPERATOR'` (migration.sql:7). A user created without an explicit role is therefore least privileged. The enum is checked by the database, so invalid roles cannot be persisted even by direct SQL.

The role is consumed by the authentication/authorization layer (auth middleware and user module in `src/`, outside the analysed component) and by the test factory (`tests/helpers/factories.ts:76`, `createTestUser` role override). The seed script creates one ADMIN (`admin@oms.local`) and one OPERATOR (`operador@oms.local`) (prisma/seed.ts:194-210).

Adding a role requires a new migration, as MySQL ENUM changes are DDL operations. No migration for that exists yet.

**Rule workflow**:
```
Create user -> role provided? yes: validated against ENUM; no: OPERATOR
```

### Business Rule: Order Lifecycle States and Default

**Overview**:
Orders have one of six statuses and start as `PENDING`. The same enum is used by `orders.status` and both status columns of the history table.

**Detailed description**:
`enum OrderStatus` (schema.prisma:16-23) defines PENDING, PAID, PROCESSING, SHIPPED, DELIVERED, CANCELLED. The migration maps it to an inline MySQL ENUM repeated in three columns (migration.sql:54, 90, 91). `orders.status` defaults to `PENDING` (schema.prisma:78), and application code explicitly sets `PENDING` upon creation (order.service.ts:99).

The schema models only the set of valid states. Which transitions are legal is not enforced by the database; it is enforced in `src/modules/orders/order.status.ts:3-10` (PENDING to PAID or CANCELLED; PAID to PROCESSING or CANCELLED; PROCESSING to SHIPPED or CANCELLED; SHIPPED to DELIVERED; DELIVERED and CANCELLED terminal). Direct SQL or the seed script can therefore write any state combination. The seed, for instance, reconstructs a valid path by hand (seed.ts:255-262) and note that for CANCELLED orders it records only PENDING -> CANCELLED regardless of whether stock effects would apply.

Because the enum is duplicated in three columns, adding a state requires altering all three columns in a migration.

**Rule workflow**:
```
Order created -> PENDING
changeStatus(to) -> application validates transition -> orders.status updated + history row inserted
```

### Business Rule: Product Defaults and Catalog Attributes

**Overview**:
Products default to `stockQuantity = 0` and `active = true`. Price is a required integer in cents. Description is optional.

**Detailed description**:
`Product` (schema.prisma:56-72) defines `priceCents Int` (required, no default), `stockQuantity Int @default(0)`, `active Boolean @default(true)`, and `description String? @db.Text`. Indexes on `active` and `name` support catalog filtering and search (the product repository filters by `active` and by `contains` on name/sku, src/modules/products/product.repository.ts:13-24). Note that a `contains` search compiles to `LIKE '%term%'`, which cannot use the `name` B-tree index effectively; the index mainly benefits ordering/equality (analysis note, confidence: high on MySQL semantics).

Integer columns are signed 32-bit (`INTEGER`), so maximum values are 2,147,483,647 cents (about 21.4 million currency units) per amount, and the same ceiling applies to stock quantity. The schema has no CHECK constraint preventing negative price or stock; stock negativity is prevented in application code by `debitStock` (order.service.ts:204-231), which verifies availability before decrementing.

Inactive products cannot be ordered: `OrderService.create` throws `UnprocessableEntityError('INACTIVE_PRODUCT')` (order.service.ts:66-73). The `active` flag acts as a soft-disable, since hard deletion is blocked once the product appears in an order item (see referential integrity rule).

**Rule workflow**:
```
Create product (no stock/active specified) -> stock 0, active true
Order creation -> active check in application
PENDING->PAID -> stock availability check -> decrement
```

### Business Rule: Money as Integer Cents and Order Totals

**Overview**:
All monetary amounts are integers in minor units; orders carry subtotal, discount, and total, and items carry unit price and line total.

**Detailed description**:
Columns `products.priceCents`, `orders.subtotalCents`, `orders.discountCents` (default 0), `orders.totalCents`, `order_items.unitPriceCents`, and `order_items.totalCents` are all `INTEGER` (migration.sql:37, 55-57, 77-78). This avoids floating-point rounding errors. Currency is not stored, so a single implicit currency is assumed (the seed data suggests BRL; ambiguity, since nothing in the schema declares it).

Totals are stored (denormalized) rather than computed on read. The application computes `subtotal = sum(unitPrice * quantity)` and `total = subtotal - discount` server side, rejecting discounts larger than the subtotal (order.service.ts:86-92). The database does not verify that `totalCents = subtotalCents - discountCents` or that item totals match, so consistency depends entirely on the code path; the seed computes the same formulas (seed.ts:281-283) with a 5% discount (floored) on every seventh order.

Storing `unitPriceCents` on `order_items` is a price snapshot: later changes to `products.priceCents` do not alter historical orders. This is a core invariant for order history correctness.

**Rule workflow**:
```
Read product prices -> unitPriceCents snapshot -> line total = unit * qty
subtotal = sum(lines) ; discount <= subtotal ; total = subtotal - discount ; persist all
```

### Business Rule: Referential Integrity and Deletion Behaviour

**Overview**:
Foreign keys restrict deletion of referenced customers, users and products, and cascade deletion from orders to their items and history.

**Detailed description**:
Six foreign keys are created (migration.sql:110-125). `orders.customerId -> customers.id` and `orders.createdById -> users.id` are `ON DELETE RESTRICT`; `order_items.productId -> products.id` is `RESTRICT`; `order_status_history.changedById -> users.id` is `RESTRICT`. `order_items.orderId` and `order_status_history.orderId` reference `orders.id` with `ON DELETE CASCADE`. All use `ON UPDATE CASCADE`. Prisma defaults are used for the non-cascade relations (no explicit `onDelete`) (schema.prisma:87-88, 109, 126).

Consequences: a customer, user, or product that appears in any order cannot be deleted. The customer and product services call `delete` after only an existence check (src/modules/customers/customer.service.ts:60-63, src/modules/products/product.service.ts:63-66). When the FK blocks deletion, Prisma raises `P2003`, which the error middleware does not map (only P2002 and P2025 are mapped), so the client would receive a generic HTTP 500 rather than a 409 (risk, see section 10).

Deleting an order (permitted by the service only in PENDING or CANCELLED status, order.service.ts:184) removes its items and its history through cascade. This means that audit history for a deleted order is permanently lost. Because the history table's `changedById` is RESTRICT, users who ever changed an order status also cannot be deleted.

**Rule workflow**:
```
DELETE customer/product/user referenced by orders -> MySQL error 1451 -> Prisma P2003 -> HTTP 500 (unmapped)
DELETE order (PENDING/CANCELLED) -> order_items and order_status_history cascade-deleted
```

### Business Rule: Order Status History (Audit Trail)

**Overview**:
Each status change is recorded in `order_status_history` with previous status, new status, author, timestamp and optional reason.

**Detailed description**:
`OrderStatusHistory` (schema.prisma:116-131) holds `fromStatus` (nullable), `toStatus`, `changedAt` (default now), `changedById`, and `reason VARCHAR(500)` (nullable). `fromStatus` is NULL for the creation entry, which the service writes with reason "order created" (order.service.ts:106-113). Subsequent entries are written in the same transaction as the status update (order.service.ts:158-167), so the status and its audit row are committed atomically.

Indexes on `orderId` and `changedAt` support retrieving a timeline; the repository reads history ordered by `changedAt asc` (order.repository.ts:56). There is no `updatedAt` and no update/delete path in the service, making the table append-only in practice (not enforced by the database).

Ordering relies on `changedAt` with millisecond precision (`DATETIME(3)`); entries created in the same millisecond have undefined relative order (low-probability edge case; the seed inserts multiple history rows per order quickly in sequence, so ties are plausible there).

**Rule workflow**:
```
changeStatus tx: update orders.status -> insert history(from,to,user,reason) -> commit
Read order -> history sorted by changedAt ascending
```

### Business Rule: Order Number Sequence

**Overview**:
Human-readable order numbers `ORD-000001` style are generated from a single-row counter table.

**Detailed description**:
`OrderNumberSequence` (schema.prisma:133-138, table `order_number_sequence`) has `id` default 1 and `nextValue` default 1. The service performs `upsert({ where: {id: 1}, create: {id:1, nextValue:2}, update: {nextValue: {increment: 1}} })` inside the order transaction and derives `current = nextValue - 1`, formatted with six-digit zero padding (order.service.ts:245-254). First order thus gets `ORD-000001` (create branch stores 2) and later orders increment.

Since the increment occurs within the same transaction as the order insert, a rolled-back order creation also rolls back the counter increment, so numbers have no gaps from failed creations. The row-level lock taken by the UPDATE serializes concurrent creators on this row, guaranteeing uniqueness (also protected by the unique index on `orders.orderNumber`) but making order creation a serialization point (throughput risk). The first-ever concurrent calls could race on the insert branch of upsert; the unique primary key would make one fail (confidence: medium; behaviour depends on Prisma upsert emulation for MySQL).

The `VARCHAR(20)` limit on `orderNumber` comfortably holds the format. After 999,999 orders the padding no longer limits digits (padStart does not truncate), so numbers just grow longer. The seed duplicates this function (seed.ts:165-176), so logic exists in two places.

**Rule workflow**:
```
tx begin -> upsert order_number_sequence(id=1) -> current = nextValue-1 -> "ORD-" + pad6(current) -> insert order -> commit
```

### Business Rule: Customer Address and Document Storage

**Overview**:
Customer address is a required JSON column; document (tax id) is a free-form string up to 20 chars with a non-unique index.

**Detailed description**:
`address Json` (schema.prisma:46) maps to MySQL `JSON NOT NULL` (migration.sql:22). The schema imposes no structure on it; the seed and test factory both use `{street, number, city, state, zipCode}` (prisma/seed.ts:15-21; tests/helpers/factories.ts:51-57). Structure validation, if any, is in `src/modules/customers/customer.schemas.ts` (outside this component).

`document VARCHAR(20)` accommodates formatted CPF (`123.456.789-00`, 14 chars) and CNPJ (`12.345.678/0001-90`, 18 chars), both used in seed data. No format or checksum validation exists at the schema level, and seed CPFs/CNPJs are fictitious. The `@@index([document])` (schema.prisma:52) suggests lookup by document is anticipated.

`phone VARCHAR(32)` is stored as free text (seed uses E.164-like values).

**Rule workflow**:
```
Customer create -> address JSON (not null) + document string -> indexed lookup by document possible; no DB-level format checks
```

### Business Rule: Identifier and Timestamp Conventions

**Overview**:
All tables use UUID primary keys generated by Prisma and `createdAt`/`updatedAt` timestamps with millisecond precision.

**Detailed description**:
`id String @id @default(uuid()) @db.Char(36)` is used on every table except `order_number_sequence` (Int). UUID generation happens in the Prisma client (the SQL has no DEFAULT for ids), so inserts via raw SQL must supply ids. `createdAt` uses `DEFAULT CURRENT_TIMESTAMP(3)`; `updatedAt` has no database default (`DATETIME(3) NOT NULL`, migration.sql:9 etc.) and relies on `@updatedAt`, which Prisma fills client-side. Raw SQL inserts without `updatedAt` would fail (NOT NULL without default).

`order_items` and `order_status_history` lack `updatedAt`, consistent with their immutable nature. All tables use `utf8mb4` with `utf8mb4_unicode_ci` collation (migration.sql, matching docker-compose server settings), so string comparisons (including the unique email index) are case-insensitive. Consequently `A@x.com` and `a@x.com` conflict at the database level.

Table names are snake_case plural through `@@map`, while column names remain camelCase (no `@map` on fields).

**Rule workflow**:
```
Prisma create -> client generates uuid; createdAt via DB default; updatedAt set by Prisma on create/update
```

### Business Rule: Order Status Transitions and Stock Effects (Application, schema-dependent)

**Overview**:
The schema stores `stockQuantity` and `status`; the transition matrix and stock side effects are applied in code.

**Detailed description**:
Allowed transitions: PENDING to {PAID, CANCELLED}; PAID to {PROCESSING, CANCELLED}; PROCESSING to {SHIPPED, CANCELLED}; SHIPPED to {DELIVERED}; DELIVERED and CANCELLED are terminal (src/modules/orders/order.status.ts:3-10). A transition to the same status raises a Conflict (order.service.ts:140-146).

Stock is debited only at PENDING to PAID (order.status.ts:24-31): the service reads products, collects shortages and throws `InsufficientStockError` (HTTP 422 per test tests/orders.test.ts:109) if any item lacks stock, otherwise decrements each product (order.service.ts:204-231). Stock is replenished when going from PAID or PROCESSING to CANCELLED (order.status.ts:33-37). Cancelling from PENDING involves no stock changes since nothing was debited. Cancelling from SHIPPED is not allowed.

The check-then-decrement sequence is within a transaction but without explicit row locks (`SELECT ... FOR UPDATE`) and the schema has no CHECK `stockQuantity >= 0`. Under MySQL's default REPEATABLE READ isolation, two concurrent PENDING-to-PAID transitions for the same product could both pass the read check and both decrement, driving stock negative (risk, confidence: medium; depends on interleaving).

**Rule workflow**:
```
changeStatus tx -> load order+items -> validate transition
  PENDING->PAID: check stock -> decrement or 422
  PAID|PROCESSING->CANCELLED: increment stock
-> update status -> insert history -> commit
```

### Business Rule: Order Deletion Constraint (Application, schema-dependent)

**Overview**:
Orders can be deleted only in PENDING or CANCELLED status; deletion cascades.

**Detailed description**:
`OrderService.delete` loads the order, rejects states other than PENDING or CANCELLED with `ConflictError('INVALID_ORDER_STATE_FOR_DELETE')` (order.service.ts:181-192), then deletes. The cascading FKs remove items and history. A test covers the rejection path (tests/orders.test.ts:197).

Since a CANCELLED order deleted after having had stock replenished leaves stock consistent, and a PENDING order never debited stock, deletion is stock-neutral under the rules. The check and delete are not in one transaction (read then delete), so a status change between them could allow deletion of an order that moved to PAID (narrow race window; confidence: medium).

**Rule workflow**:
```
find order -> status in {PENDING, CANCELLED}? no: 409 ; yes: DELETE orders row -> cascade items/history
```

### Business Rule: Seed Dataset Generation

**Overview**:
The seed script resets the database and builds demo users, customers, products, and 26 orders across all statuses with plausible history.

**Detailed description**:
The seed first deletes all rows in FK-safe order: history, items, orders, products, customers, users, sequence (seed.ts:181-187). It then creates the users with bcrypt cost 10 and fixed passwords `admin123` / `operator123` (seed.ts:6-7, 191-210), 10 customers (6 CPF individuals plus 2 CNPJ companies among them, remaining individuals), and 20 products with price/stock values (seed.ts:142-163).

Orders follow an `ordersPlan` (seed.ts:226-253): 4 PENDING, 5 PAID, 4 PROCESSING, 4 SHIPPED, 6 DELIVERED, 3 CANCELLED. Customers are assigned round-robin, authors alternate (admin for every third order), a 5% floor discount applies to every seventh order, and prices are snapshotted. Status history is generated from `flowFromStatus` (seed.ts:255-262), emitting one row per step with reason `seed transition X->Y`.

Seeding bypasses the service layer: stock is not debited for PAID/PROCESSING/SHIPPED/DELIVERED seeded orders, so seeded stock values are not consistent with the application's stock rule (inconsistency between seed data and business rule; confidence: high). Also the CANCELLED path records only PENDING to CANCELLED even though the plan is independent of prior payment. A typo exists in a product name (`Caneta Pilot G2 Pretra`, seed.ts:162).

**Rule workflow**:
```
clean tables -> users -> customers -> products -> for each plan: reserve number, create order+items, create history chain
```

### Business Rule: Migration Management and Provider Lock

**Overview**:
Schema evolution is managed through Prisma Migrate with a MySQL provider lock and a shadow database.

**Detailed description**:
`migration_lock.toml` pins `provider = "mysql"`, preventing accidental use of other providers (prisma/migrations/migration_lock.toml:3). The datasource defines `shadowDatabaseUrl` from `SHADOW_DATABASE_URL` (schema.prisma:8), required by `prisma migrate dev` on MySQL; `.env.example` points it at a separate `oms_shadow` database using the root user, because creating/dropping shadow databases needs elevated privileges (.env.example:5).

A single migration `20260519182739_init` creates the entire schema. Scripts: `db:migrate` (`prisma migrate dev`), `db:reset` (`prisma migrate reset --force`, which drops data without prompt), `db:seed` (package.json:13-15). The `prisma.seed` config in package.json:26-28 makes `prisma migrate reset` auto-run the seed with `tsx prisma/seed.ts` (note this variant lacks `--env-file`, while `db:seed` includes it).

No production deployment command (`prisma migrate deploy`) is defined in package.json scripts (observation, deployment may be documented elsewhere).

**Rule workflow**:
```
edit schema -> migrate dev (shadow DB diff) -> new migration dir -> applied -> client regenerated
reset -> drop, re-apply all migrations -> seed
```

## 9. Design Patterns & Architecture

| Pattern | Implementation | Location | Purpose |
|---------|----------------|----------|---------|
| Schema-first ORM | Prisma schema generates client and SQL | prisma/schema.prisma | Single source of truth for model |
| Versioned migrations | Prisma Migrate with timestamped folders and lock file | prisma/migrations | Reproducible schema evolution |
| Repository Pattern (consumer) | `*Repository` classes wrapping PrismaClient | src/modules/*/ *.repository.ts | Data access abstraction |
| Unit of Work / Transaction script | `prisma.$transaction` callbacks and arrays | order.service.ts:58,131; repositories list() | Atomic multi-write operations |
| Audit log table | order_status_history | schema.prisma:116 | Status change traceability |
| Sequence table | order_number_sequence single row | schema.prisma:133 | Application-managed sequential numbering |
| Snapshot of price | order_items.unitPriceCents | schema.prisma:104 | Historical price integrity |
| Denormalized totals | subtotal/discount/total columns | schema.prisma:79-81 | Read efficiency and immutability of totals |
| Dependency Injection (manual) | PrismaClient passed through `buildApp({ prisma })` | src/app.ts:23-66 | Testability, composition root |

| Soft disable | Product.active | schema.prisma:63 | Retire products without deleting |
| Seed/fixture | seed.ts | prisma/seed.ts | Demo and development data |

## 10. Technical Debt & Risks

| Risk Level | Component Area | Issue | Impact |
|------------|----------------|-------|--------|
| High | order_status_history / orders FK | Unmapped Prisma error P2003 (FK RESTRICT) when deleting customers/products referenced by orders; error middleware maps only P2002 and P2025 (error.middleware.ts:37-56) | Client receives HTTP 500 instead of a 409 conflict |
| High | Stock handling (products.stockQuantity) | No CHECK constraint and no row locking around read-then-decrement (order.service.ts:204-231) | Possible negative stock under concurrent PENDING->PAID transitions |
| Medium | Domain invariants | No DB-level checks for non-negative price/stock/quantity, positive quantity, total = subtotal - discount, or valid status transitions | Invalid data possible via direct SQL, seed, or bugs |
| Medium | order_number_sequence | Single-row counter updated in every order creation; first-insert race on upsert | Serialization bottleneck; possible transient failure on concurrent first order |
| Medium | Cascade delete on orders | Deleting an order removes its audit history | Loss of audit trail |
| Medium | Seed data | Seeded PAID/PROCESSING/SHIPPED/DELIVERED orders do not debit stock; credentials hard-coded (`admin123`, `operator123`); script deletes all data without environment guard | Inconsistent demo data; accidental data wipe or weak credentials if run in a shared environment |
| Medium | Seed duplication | `reserveOrderNumber` and status-flow logic duplicated from service | Drift risk between seed and application |
| Low | Enums inline in MySQL | OrderStatus ENUM duplicated across three columns | Multi-column ALTER needed for new states |
| Low | Integer 32-bit money/stock | `INTEGER` for cents | Overflow ceiling about 21.4 million currency units per amount |
| Low | Customer.document not unique | Duplicate documents allowed | Possible duplicate customers (intent unclear) |
| Low | Product name search | `contains` produces LIKE '%x%'; index on name has limited benefit | Full scans on large catalogs |
| Low | Schema formatting | Misaligned fields in Order, OrderStatusHistory, OrderNumberSequence models | Cosmetic; `prisma format` drift |
| Low | Seed data quality | Typo "Pretra" in product name (seed.ts:162) | Cosmetic |
| Low | Single migration, no deploy script | Only `init` migration; no `migrate deploy` script in package.json | Production rollout procedure not visible in repo |
| Low | updatedAt without DB default | Raw SQL inserts must supply updatedAt | Operational friction for non-Prisma writers |
| Low | Status history ordering | Ordering by `changedAt` at ms precision, no sequence column | Ambiguous order for same-millisecond rows |
| Low | Delete order check-then-act | Status read and delete not in same transaction (order.service.ts:181-192) | Narrow race to delete a just-paid order |
